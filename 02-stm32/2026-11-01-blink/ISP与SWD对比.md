# ISP 烧录 vs SWD 下载

> 2026-11-01 当天学习产出。**先动手点灯，再回来填这张表**——空着写不出来，写着写着就懂了。
> 填完这一页，「为什么 STM32 调试这么方便」这个问题你就答得出来了。

## 一、先认清两个词不是一回事

| 名称 | 是什么 | 用在哪 |
|---|---|---|
| **ISP**（In-System Programming） | 芯片出厂固化在内部的一段引导程序，上电先跑它，通过特定引脚接收新程序 | 51 单片机主要靠这个 |
| **SWD**（Serial Wire Debug） | ARM 的调试接口协议，两根线，既能下载程序也能**在运行时读写 CPU 内部状态** | STM32 等 Cortex-M 芯片 |

一句话区别：**ISP 只能"换程序"，SWD 能"边跑边看"**。

## 二、逐项对比

| 维度 | 51 的 ISP | STM32 的 SWD |
|---|---|---|
| 全称 | In-System Programming（在系统编程） | Serial Wire Debug（串行线调试） |
| 需要几根线、哪几根 | **3 根**：TXD→P3.0(RXD)、RXD→P3.1(TXD)、GND。收发必须交叉接 | **4 根**：3V3、GND、SWDIO(PA13)、SWCLK(PA14)。板子自己供电时可省掉 3V3，**最少 3 根** |
| 除了开发板还需要什么硬件 | USB 转串口（CH340/PL2303，板载或外接模块）。**不需要专用下载器** | **ST-Link**（或 J-Link / DAP-Link）。这是专用调试器，不是简单的电平转换 |
| 烧录时芯片在跑什么 | 跑出厂固化的 **ISP 引导程序**。它只在上电/复位后的一小段时间里监听串口 | 芯片本身不需要跑东西。ST-Link 通过 SWD 直接操作 **Flash 控制器**和内核调试逻辑 |
| 烧录时程序还在正常运行吗 | **不能**。已经复位进入引导程序，用户程序是停的 | 写 Flash 时一般会 halt 内核，但**调试时能随时停、随时跑**——这正是它的价值 |
| 能不能打断点、单步、看变量 | **不能**。只能"下载 → 复位 → 看现象"，程序里发生了什么全靠猜 | **能**。断点、单步、看寄存器/变量/内存，还能读 CPU 实时执行流（SWO） |
| 要不要"断电再上电" | **芯片层面必须**：引导程序只在上电那一瞬间检查串口。但我这块尚硅谷板子带 **CH340 的 DTR/RTS 自动下载电路**——STC-ISP 点下载时软件把 DTR/RTS 拉低，硬件用这个信号**切断再恢复 MCU 供电**，等于替我做了"断电→上电"，所以感觉不到要冷启动。没有这个电路的板子/模块就必须手动断电 | **不用**。`Reset and Run` 勾上，下载完自动复位运行 |
| 一次下载大概多久 | 2~3 秒（8KB Flash，取决于串口波特率） | 1~2 秒（512KB Flash，ST-Link 全速） |
| 改一行代码到看见现象，总共几步 | **3 步**（有自动下载电路时）：改代码 → Keil 编译(F7) → STC-ISP 点下载，板子自动断电上电。没这个电路就是 **4 步**，多一步手动断电再上电 | **3 步**：改代码 → F7 编译 → F8 下载（自动复位运行） |
| 程序把下载引脚复用掉了，怎么救回来 | 不会发生。ISP 走的是 UART（P3.0/P3.1），而且**引导程序优先级最高**，程序写坏了照样能重下 | **会**。PA13/PA14 被配成 GPIO 后就连不上了，救法见第三节第 3 问 |

## 三、三个必须能答的追问

**1. SWD 只用两根线（SWDIO + SWCLK），凭什么既能下载又能调试？**

SWDIO 是双向数据线、SWCLK 是时钟，两根线构成一条同步串行总线。协议层上是两类事务：

- 访问 **AHB-AP**：能直接读写芯片的**整个地址空间**——Flash 控制器、RAM、任意外设寄存器。下载程序就是往 Flash 控制器里写
- 访问 **DP 寄存器**：控制内核的 halt / step / 断点

关键在于：这些操作由 CPU 外围的**调试逻辑**完成，**不需要 CPU 执行任何指令**。所以程序在跑、甚至跑飞了，也能读它的状态、把它按停。

**2. 为什么 51 的 ISP 要"冷启动"——点了下载还得手动断电再上电？**

ISP 引导程序固化在芯片里，**复位向量指向它**。上电/复位后它先跑，在最初几百毫秒内监听串口：

- 收到下载命令 → 进下载模式，接收新程序写进 Flash
- 没收到 → 跳到用户程序区开始跑

**一旦跳走，串口就再也不被监听了。** 所以必须让芯片重新上电，重新给它一次"选择的机会"——这就是"先点下载、再上电"的顺序不能反的原因。

> **补充（11-01 实测的疑问）**：我的尚硅谷板子在 STC-ISP 里点下载就直接成功，不用手动断电。**不是芯片变了，是板子把这一步自动化了**：CH340 的 `DTR`/`RTS` 被 STC-ISP 软件控制，点下载时它们拉低，板上一个小电路（两个 MOS 管 + 电容充放电）借此把 MCU 的 VCC 断开几十毫秒再接通——用硬件模拟了"手拔电源再插上"。所以"需不需要冷启动"取决于两件事：**芯片的引导程序在什么时机检查串口** + **板子上有没有自动控制电源的电路**。缺一条才要你动手。

**3. STM32 上如果把 PA13/PA14 配成了普通 GPIO，下次连不上了怎么办？**

三条路，从轻到重：

- **Connect under Reset**：Keil → `Debug → Settings → Debug` 页，`Connect` 选 `under Reset`；然后**按住板上复位键 → 点下载 → 松手**。ST-Link 会在内核执行到 GPIO 初始化那几行之前抢占 SWD 口
- **拉高 BOOT0**（BOOT0=1、BOOT1=0）从系统存储器启动，芯片跑 ST 固化的 Bootloader 而不是你的程序，此时 SWD 一定是通的，连上后擦掉 Flash
- 用 **STM32CubeProgrammer / ST-Link Utility** 全片擦除

预防办法就是今天 CubeMX 里那一步：`SYS → Debug = Serial Wire`（千万别留 `Disable`）。这样生成的 `HAL_GPIO_Init()` 不会去动 PA13/PA14。

## 四、今天实测记录

| 项目 | 51 | STM32 |
|---|---|---|
| 用的软件 | Keil C51（V9.61）+ STC-ISP v6.96 | STM32CubeMX + Keil MDK-ARM 5.38 |
| 实际耗时（从改代码到看见现象） | 建工程 00:18 → 生成 hex 00:24，**约 6 分钟** | 16:07 生成工程 → 23:46 最后一次编译烧录。中间大半时间耗在排查下载器识别和时钟配置上 |
| 第一次就成功的吗，卡在哪 | 一次过。原因是板载 CH340 带 **DTR/RTS 自动下载电路**，点下载时板子自己断电再上电，我没动手 | **不是**。卡在 Keil 里 `Debug Adapter → Unit` 为空、`SW Device` 报 `No ST-LINK detected`——是**下载器没被电脑认出**，跟 SWD 接线无关；CubeMX 两处：`System Wake-Up` 抢 PA0、时钟树漏配 `System Clock Mux` |
| 灯亮时的引脚和电平 | P0.0，**低电平点亮**（`LED = 0`）。注意 P0 无内部上拉，能亮说明板子是共阳接法 | PA0，**低电平点亮**。CubeMX 里 `GPIO output level` 设 `High` 是为了上电默认灭，不闪一下 |

> 耗时一栏是按实际时间戳估的，跟你印象不符就直接改。

## 五、我的结论（写给三个月后的自己）

> 下次再有人问"51 和 STM32 下载方式有什么区别"，我希望我能不假思索地说出：
>
> 51 的 ISP 是"把程序推进去，然后祈祷"——只能看结果，出了问题只能靠改代码试；
> STM32 的 SWD 是"程序跑着的时候我能把手伸进去"——断点、单步、看变量、看寄存器。
> 差的不是下载速度，是**排错能力**。这就是为什么后面 40 天真正干活的都是 SWD，
> 而 ISP 只是我理解"引导程序"这个概念的历史入口。

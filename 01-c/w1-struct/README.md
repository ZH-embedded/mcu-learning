## 今天真正要拿下的 6 个认知

### 1. 结构体的大小 ≠ 成员大小之和

```c
typedef struct { char a; int b; char c; } probe_t;    /* 1 + 4 + 1 = 6，sizeof 却是 12 */
```

`p01` 的 `main` 会直接打印出来：

```
offsetof 实测：a=0  b=4  c=8
```

偏移 1、2、3 是编译器塞的填充，`a` 后面的 3 字节是为了让 `b` 落在 4 的倍数上，`c` 后面 3 字节是为了让**数组里下一个元素的 `b` 也落在 4 的倍数上**。

**为什么要紧**：F103ZET6 一共 64KB RAM。1000 条记录每条多 3 字节填充，就是 3KB。老工程师写结构体时把 `char` / `u8` 堆在一起、`int` 和指针放后面，不是审美，是省内存。

`p01` 的 TODO 2 就是让你算这个数——**别写死 6，用 `sizeof` 减**，以后改成员类型它自动跟着对。

### 2. `offsetof` 是唯一能"问编译器要布局"的办法

```c
offsetof(sensor_t, value)     /* 16 */
```

`p01` 的 TODO 3 用它。这个词在调试时很有用：串口收来一帧二进制数据，你要按偏移去取字段，就得知道每个字段落在第几个字节。

### 3. 结构体不能 `==`，也不该用 `memcmp`

```c
if (s1 == s2)                  /* 编译直接报错 */
memcmp(&s1, &s2, sizeof(s1))   /* 能编过，但比的是字节，包括填充区 */
```

`p06` 的 bug 1 讲的就是这个：`rec_t` 恰好没有填充，所以 `memcmp` 版本"碰巧能用"。换成 `{ char a; int id; }` 之后填充区里是栈上的垃圾，两个逻辑上相等的记录会被判不相等。

正确做法是**逐字段比较**，而且比哪些字段是业务决定的——`p01` 的 TODO 4 只比 `id`，因为 `id` 相同就算同一条记录。

### 4. 枚举在运行时就是个整数，没有任何保护

```c
typedef enum { STATE_IDLE, STATE_RUN, STATE_FAULT, STATE_COUNT } dev_state_t;
```

- `STATE_COUNT` 是**哨兵**，它自己不是合法状态，只表示"有几个"。加一个状态不用改任何边界判断。
- 编译期它帮你查名字，运行期它就是 `0/1/2`，串口里收到一个 `99` 照样能塞进 `dev_state_t`。
- 所以 `p03` 的 TODO 3 形参故意写成 `int`——**不能假设调用者给你的枚举值合法**。

`p03` 的 TODO 2 是 `STATE_NAMES[s]` 查表，必须先判范围。`p06` 的 bug 2 就是这个坑的实物版：`NAMES[99]` 读到数组外面的一段内存，被当成 `const char *` 返回，`printf("%s")` 一去解引用就崩，或者打出乱码。

### 5. 共用体：成员叠在一起，`sizeof` 是最大那个

```c
typedef union { unsigned int u32; unsigned char b[4]; } u32_u;   /* sizeof = 4，不是 8 */
```

写 `u.u32 = 0x01020304`，再读 `u.b[0]`：

- 小端（x86 / ARM Cortex-M）：`0x04`——最低地址放最低有效字节
- 大端：`0x01`

`p04` 的 TODO 1 就是用这个原理探字节序。这件事重要是因为**串口协议、Flash 里存的 int、网络长度字段都约定了字节序**，你按反的去解释，得到的是一个完全不相关的数，而且不报错。

`p04` 的 TODO 2 打包时有个坑：`r << 24` 里 `r` 先被提升成 `int`，`r >= 128` 时会顶到符号位，**有符号溢出（UB）**——和昨天比较器 `a - b` 是同一类问题。移位前先转 `unsigned`。

### 6. 数组还是链表：先看数据怎么用

| | 数组 | 链表 |
|---|---|---|
| 长度 | 编译期定死 | 运行时增减 |
| 内存 | 连续一块 | 散在堆上，每个节点多一个指针 |
| 按下标取 | O(1) | O(n) |
| 插入删除 | 要搬家 | 只改指针 |
| RAM 碎片 | 不会 | 频繁 malloc/free 会 |

传感器记录这种"**条数基本不变、经常整表遍历、偶尔按 id 查一条**"的场景，数组几乎总是对的。11-05 会专门做链表，到时候你会看到它在 MCU 上多出来的那些麻烦。

## `p05` 是今天的产出，要能当面讲

`p05_sensor_table.c` 就是计划里那句"定义传感器数据结构体，用数组存 10 条记录并排序打印"。四个 TODO 串成一条流水线：

```
SENSOR_ROM（const，10 条，放 Flash）
      │  load_table      拷一份到 RAM（要排序就得能改）
      ▼
   ram[10]
      │  sort_table      插入排序，比较器当参数传
      ▼
   ram[10] 已排序
      │  filter_above    筛出 value > 50 的，条数走输出参数
      ▼
   big[4]
      │  print_table     打印（已给你）
      ▼
   屏幕上那张表
```

三个要点：

1. **`SENSOR_ROM` 是 `const`**，所以必须拷一份才能排序。原始数据永远有一份干净的备份——这是 `const` 的直接收益。
2. **`sort_table` 和昨天的 `sort_by` 是同一份代码**，只是元素从 `int` 换成了 20 字节的结构体，比较器从 `int(*)(int,int)` 换成了 `int(*)(const sensor_t*, const sensor_t*)`。传 `cmp_by_id` 就是按 id 排，传 `cmp_by_value_desc` 就是按 value 倒序，**一行都没改**。
3. **`filter_above` 有两个信息要出去**（筛出几条 + 每条是什么），所以条数只能走输出参数 `int *dst_n`。这就是昨天 `run_command` 那个"返回值够不够表达"问题的另一面。

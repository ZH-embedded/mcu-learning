## 六道题的顺序是有讲究的

**p01 → p02** 是「先用位域，再问它到底怎么排」。写完 p01 的 `flag_set`（8 个 case 的 switch）再写 `flag_set_raw`（三行字节指针），你会自己得出一个结论：**位域不适合动态访问**。这个结论比背十遍定义都牢。

**p03** 是今天的主菜。四个结构体的 `sizeof` 和 `offsetof` 我全部写成了断言，你要做的是**先在纸上算，再跑**。算错了不要紧，跑一遍就知道差在哪 —— 但顺序不能反，先跑一遍把数字抄下来，这道题就白做了。

**p04** 表面在讲 `sizeof`，实际在讲「编译期 vs 运行期」。`sizeof(i++)` 里的 `i++` 一次都不会执行，因为 `sizeof` 只需要类型，不需要值。

**p05 → p06** 是同一个主题的两面：p05 教你**怎么写对**线格式，p06 展示**写错了会怎样**。p06 的 bug4 有个特殊之处 —— 它在 x86 上跑得好好的，测试也是绿的，只有上了 Cortex-M 才会 HardFault。**测试全绿不等于代码正确**，这是今天第二个重点。

## 对齐规则，三条

记这三条，`sizeof` 就不用背表：

1. **每个成员的偏移**，必须是它自身对齐数的整数倍（`char` 1、`short` 2、`int` 4、`double` 8、指针 8）
2. **结构体总大小**，必须是「最大成员对齐数」的整数倍（不够就末尾补齐）
3. **填充字节里是垃圾**，不能 `memcmp`、不能直接发到线上

推论：

- 成员按**从大到小**排列通常能省内存（把 `char` 都堆到末尾）
- 数组的每个元素都按规则补齐，`s1_t[2]` 是 24 而不是 9 + 3
- `#pragma pack(1)` 能取消填充，代价是成员地址可能不对齐 —— 在允许非对齐访问的核上是省钱，在不允许的核上是 HardFault

## 认知清单（做完再看，别当背景读）

**位域**

- 位域只是「按位切分一个存储单元」的语法糖，底层仍然是那个整数类型
- 基类型决定**存储单元多大**：`unsigned char x:1` 八个 → 1 字节；`unsigned int x:1` 八个 → 4 字节，白白浪费 3 字节
- 位域**没有地址**，不能 `&` 取地址，也就不能当 `scanf` 的参数
- 位域**没有运行时下标**，`f->bit[i]` 写不出来，只能 `switch` 或自己按位算
- 位序（谁占 bit0）是**实现定义**的。gcc 小端是从最低位开始，别的编译器可能相反。**跨平台协议绝对不能用位域定线格式**
- 位的符号性由基类型决定：`int flag:1` 只有 0 和 **-1**；`char flag:1` 在 x86 上同样是有符号 → 1 变成 -1。**永远写 `unsigned`**
- 位域可以跨存储单元边界：`short lo:4, hi:5` 的 `hi` 从 bit4 开始、横跨两个字节

**对齐**

- 对齐是**硬件要求**，不是编译器洁癖：Cortex-M 的 `LDR` 要求 4 字节对齐，非对齐直接 UsageFault
- `#pragma pack(1)` 取消了填充，但**没有取消访问要求**。packed 结构体的成员地址可能不是 4 的倍数，此时不能强转成 `uint32_t *` 解引用，只能用 `memcpy` 或逐字节读
- 结构体的大小一定是「最大对齐数」的倍数，所以 `{char;int;}` 是 8 不是 5
- 通信协议**不要**直接发结构体：填充字节是垃圾、字节序和位序都依赖平台。必须有显式的序列化/反序列化函数

**`sizeof`**

- 是**运算符**不是函数，在编译期求值，操作数不进代码（`sizeof(i++)` 不改 `i`）
- 结果是 `size_t`（无符号）。`sizeof(x) - 1` 在 `x` 为 0 时会变成天文数字，比较时尤其致命
- 数组作形参会**退化成指针**，函数里的 `sizeof(arr)` 永远是指针大小。求元素个数只能额外传 `n`，或者用 `ARRAY_LEN` 宏（只在数组可见的作用域有效）
- `sizeof(char)` 恒为 1，`sizeof(int)` 至少 2（实际看平台），**不要假设 `int` 是 4 字节**

## 今天真正要拿下的 6 个认知

### 1. 链表和数组到底是什么关系

同样存 5 个数，两种活法：

| | 数组 | 单链表 |
|---|---|---|
| 内存 | 一整块连续 | 5 块散落在堆上，靠指针串起来 |
| 按下标访问 | O(1)，`a[i]` 一条 `ldr` | O(n)，只能从头走 |
| 头插 | O(n)（后面全要挪） | **O(1)**，改两个指针 |
| 按值删除 | O(n) 找 + O(n) 挪 | O(n) 找 + **O(1)** 删 |
| 内存开销 | 只有数据 | 每个结点多一个指针（64 位 8 字节，32 位 4 字节） |
| RAM 预算 | 编译期就知道 | **运行期才知道**，这是嵌入式最忌讳的一点 |

一句话：**数组换的是"连续"，链表换的是"可插拔"**。

### 2. 头插的两行，顺序不能反

```c
n->next = l->head;      /* 先接上旧的头 */
l->head = n;            /* 再让头指向新结点 */
```

反过来的话，`l->head = n` 先把旧头的位置覆盖掉了，旧链表整条**永远找不回来**——不是"顺序错了也能跑"，是内存泄漏 + 数据丢失，而且程序不崩，测试里表现为"插了一个，剩下的一夜之间没了"。

### 3. 尾插的空表分支

```c
if (l->head == NULL) {
    l->head = n;        /* ← 最容易漏的一行 */
} else {
    /* 走到最后一个结点，p->next = n */
}
```

空链表时新结点既是头也是尾。只写 `p->next = n` 的版本在空表上会直接解引用 `NULL`；只更新 tail 不更新 head 的版本会让 `head` 永远是 `NULL`——链表里明明有数据，`size()` 也说有 1 个，但**遍历不出来**。测试第 ③ 组第一条断言就是抓这个的。

### 4. 删除必须同时握着"前驱"

单链表只能单向走，你没有"回头路"。所以删 `cur` 之前必须知道 `prev`：

```c
prev = NULL;  cur = l->head;
while (cur != NULL) {
    if (cur->value == v) {
        if (prev == NULL) l->head = cur->next;   /* 删的是头，没有前驱 */
        else              prev->next = cur->next;
        free(cur);
        l->count--;
        return 1;
    }
    prev = cur;
    cur  = cur->next;
}
```

`prev == NULL` 这个分支就是"删头结点"。真实项目里更常见的写法是加一个**哑结点（dummy head）**：
`list_t` 里放一个不存数据的头结点，这样"删第一个"和"删中间"就是同一段代码，少一个分支。代价是多一个结点的内存，以及所有遍历要跳过它。

### 5. `free` 之前先把 `next` 存下来

```c
list_node_t *next = p->next;   /* 先存 */
free(p);                       /* 再释放 */
p = next;                      /* 最后前进 */
```

顺序反了就是 **use-after-free**：`free(p)` 之后那块内存已经不归你了，再读 `p->next` 是未定义行为。阴险的地方在于 `-O0` 下那块内存往往还没被复用，读出来居然是对的；等开了 `-O2` 或者堆一忙，就开始随机崩。

`remove` 里同理：`free(cur)` 之后不能再碰 `cur`。

### 6. `count` 是"第二份真相"，必须跟着改

`list_t` 里存 `count` 是为了让 `size()` 变成 O(1)。但代价是：**每一条改变链表的路径都要改它**。

- `push_*` 成功 → `count++`（`malloc` 失败的那条路**不能**加）
- `remove` 真的删掉 → `count--`（没找到的那条路不能减）
- `destroy` / `init` → 直接置 0

测试里的 `check_list` 不只比值序列，还比 `count`——因为"序列对、count 错"是这类代码最常见的半对状态。

## 为什么嵌入式里链表要慎用

链表在 PC 上是标配，在单片机上是要打问号的。三个理由：

**① 每次插入都是一次 `malloc`，耗时不确定。**
`malloc` 要在堆里找一块够大的空闲块，最好情况 O(1)，最坏要遍历空闲链表；碎片多了以后耗时可能差几十倍。如果这段代码跑在 1 kHz 的控制环或者中断里，**最坏执行时间（WCET）就不可分析了**——而实时系统的第一要求恰恰是"最坏情况可预测"。

**② 堆会碎。**
反复 `malloc` / `free` 不同大小的块之后，堆里会出现一堆用不上的小空洞。总空闲量看着够（比如还剩 3 KB），但最大连续块只有 40 字节，下一次申请 100 字节就失败。这个现象跑一天都复现不出来，在现场跑三天出现一次。

**③ 失败没法体面退出。**
`malloc` 返回 `NULL` 时，`push_back` 只能返回 0。可调用者往往不检查返回值，于是"以为插进去了，其实没有"——这类 bug 比崩溃更难查。

**替代方案：静态内存池。**

```c
#define POOL_N 64
static list_node_t g_pool[POOL_N];      /* 编译期就占好，RAM 预算里算得清 */
static list_node_t *g_free_list;        /* 空闲结点自己串成一条链 */

list_node_t *node_alloc(void)           /* O(1)，耗时恒定，永不失败 */
{
    if (g_free_list == NULL) {
        return NULL;                     /* 池空了 —— 这个失败是"设计内"的，可以优雅处理 */
    }
    list_node_t *n = g_free_list;
    g_free_list = n->next;
    return n;
}
```

好处：RAM 占用在编译期就定死（`64 × 8 = 512` 字节，链接脚本里看得见）、分配耗时恒定、失败可预测。
代价：上限写死，超了就得拒绝——但这在嵌入式里通常**正是你想要的**。

**结论**：不是"链表不能用"，是"**在中断/实时路径上不要用会 `malloc` 的链表**"。控制流里用静态池或定长数组，配置类、启动时初始化一次的数据用链表完全没问题。

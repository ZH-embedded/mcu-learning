## 2026-10-29 · git push 证书校验失败 / 连接被重置

**现象**：
`git push` 报 `SSL certificate problem: unable to get local issuer certificate (20)`；关掉加速软件后改报 `Recv failure: Connection was reset`，再试又变成 `Failed to connect to github.com:443 after 21046 ms`。

**复现条件**：必现。直连 GitHub 一定失败；开着加速软件时失败在证书环节。

**定位过程**：
1. `git config --list` 看 ssl/proxy → 无异常配置，`http.sslCAInfo` 指向 Git 自带的 ca-bundle，文件存在
2. `openssl s_client -connect github.com:443 -servername github.com` 看证书链 → **issuer 是 `CN=SteamTools Certificate, O=BeyondDimension`，不是 DigiCert** → 判断有本地软件在做 TLS 中间人
3. `Get-Process` / `Get-ItemProperty Internet Settings` → 发现 `Steam++`（Watt Toolkit）在运行，系统代理却是关的 → 说明它走的是自己的本地反代，不是系统代理
4. 关掉加速后再测 → 证书恢复直连但 443 超时 → 判定为链路层阻断，两件事叠加
5. `Get-NetTCPConnection -LocalPort 443` + 查 hosts → 确认加速关闭时没有任何本地监听，即加速确实没接管

**根因**：
两个独立问题叠加。① Steam++ 的 GitHub 加速用本地反代 + 自签根证书实现，而该根证书只装在 Windows 证书库，**Git 用的是 OpenSSL，不读 Windows 库**，所以校验失败；② 关掉加速后 GitHub 直连在国内被干扰，443 连不通。

**修复**：
1. 把系统证书库里的 `SteamTools Certificate` 导出为 PEM，追加到 Git 自带 ca-bundle 的副本 → `C:\Users\zhouh\.gitcerts\ca-bundle.crt`
2. `git config --global http.sslCAInfo "C:/Users/zhouh/.gitcerts/ca-bundle.crt"`（保留了全部原始 CA，只多信任这一个）
3. 重新开启 Steam++ 的 GitHub 加速后 push 成功

**如何避免**：
- 遇到"证书 issuer 不对"，先查本机代理/加速软件，**不要**用 `http.sslVerify false` 绕过——那等于对所有中间人敞开，代码可被静默替换
- 需要查 GitHub 是否可达，用 `openssl s_client` 看是"证书问题"还是"TCP 不通"，两者修法完全不同
- 本地 CA 覆盖写在 `~/.gitcerts`，不污染 Git 安装目录，重装 Git 后只需重配一行

## 2026-10-31 · strcmp 用裸 char 比较，≥0x80 字节的大小关系翻转

**现象**：
`my_strcmp` 9 条用例全过，`-Wall -Wextra` 零警告，但语义与 C 标准不一致。标准规定逐字节按 `unsigned char` 比较，实现里直接写 `a[i] > b[i]`，用的是裸 `char`。

**复现条件**：
必现，但只在字符串含 ≥0x80 的字节时暴露：
- `"\xC3\xA9"`（é）vs `"z"` → 标准返回正数（0xC3=195 > 'z'=122），该实现返回负数（`(char)0xC3` = -61 < 122）
- 纯 ASCII 输入永远不触发。所有练习题、英文标识符、数字串都在 ASCII 域内，所以测试全绿是**假象**

**定位过程**：
1. 用例全过 → 第一反应是怀疑测试漏了边界
2. 手推 `"abc" vs "abcd"`（比到 `'\0'`）、`"" vs "a"`、`"Z" vs "a"` → 都对，循环条件用 `||` 而非 `&&`，这个最容易踩的坑反而躲过去了
3. 既然边界没问题，转头查「被测值本身的类型」→ `a[i]` 是 `char`，而 C 标准对 `strcmp` 的定义是比较 `unsigned char`
4. 查 `char` 的符号性：这是**实现定义**的，x86 上的 MinGW 默认有符号，`(char)0xC3 == -61`
5. 结论：ASCII 域内两种语义完全等价，所以本地测不出来；一旦字符串来自串口原始字节（中文、0xFF 协议头）就翻转

**根因**：
C 的 `char` / `signed char` / `unsigned char` 三兄弟里，裸 `char` 的符号性由实现决定。标准库所有「按字节比较」的函数（`strcmp` / `strncmp` / `memcmp`）一律按 `unsigned char` 语义定义。直接拿 `char` 做大小比较，在字节 ≥0x80 时结果与标准相反。

**修复**：
```c
unsigned char ca = (unsigned char)a[i];
unsigned char cb = (unsigned char)b[i];
if (ca != cb) return (int)ca - (int)cb;
```

**如何避免**：
- 凡是「按字节比大小」，先转 `unsigned char` 再比。这是规则不是技巧
- 测试集必须含 ≥0x80 的字节（中文 / 0xFF），否则这类问题测不出来。纯 ASCII 全绿不代表对
- **更阴的一层**：ARM 的 AAPCS 规定裸 `char` 是**无符号**的（`arm-none-eabi-gcc` 遵守），所以这段代码在 PC 上错、烧到 STM32 上反而"对"。反过来也成立——PC 上验证过的东西，不能假设板子上行为一致。凡是依赖 `char` 符号性的代码，跨平台就是薛定谔的 bug
- 面试可这样讲：`char` 符号性是实现定义的，标准库比较函数按 `unsigned char` 定义，所以 `strcmp("é","z")` 与 `(char)` 直接比结果相反；而 ARM 与 x86 的默认符号性不同，这类 bug 只在特定平台暴露

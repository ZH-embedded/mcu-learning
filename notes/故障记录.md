## 2026-10-29 · git push 证书校验失败 / 连接被重置

**现象**：
`git push` 报 `SSL certificate problem: unable to get local issuer certificate (20)`；关掉加速软件后改报 `Recv failure: Connection was reset`，再试又变成 `Failed to connect to github.com:443 after 21046 ms`。

**复现条件**：必现。直连 GitHub 一定失败；开着加速软件时失败在证书环节。

**定位过程**：
1. `git config --list` 看 ssl/proxy → 无异常配置，`http.sslCAInfo` 指向 Git 自带的 ca-bundle，文件存在
2. `openssl s_client -connect github.com:443 -servername github.com` 看证书链 → **issuer 是 `CN=SteamTools Certificate, O=BeyondDimension`，不是 DigiCert** → 判断有本地软件在做 TLS 中间人
3. `Get-Process` / `Get-ItemProperty Internet Settings` → 发现 `Steam++`（Watt Toolkit）在运行，系统代理却是关的 → 说明它走的是自己的本地反代，不是系统代理
4. 关掉加速后再测 → 证书恢复直连但 443 超时 → 判定为链路层阻断，两件事叠加
5. `Get-NetTCPConnection -LocalPort 443` + 查 hosts → 确认加速关闭时没有任何本地监听，即加速确实没接管

**根因**：
两个独立问题叠加。① Steam++ 的 GitHub 加速用本地反代 + 自签根证书实现，而该根证书只装在 Windows 证书库，**Git 用的是 OpenSSL，不读 Windows 库**，所以校验失败；② 关掉加速后 GitHub 直连在国内被干扰，443 连不通。

**修复**：
1. 把系统证书库里的 `SteamTools Certificate` 导出为 PEM，追加到 Git 自带 ca-bundle 的副本 → `C:\Users\zhouh\.gitcerts\ca-bundle.crt`
2. `git config --global http.sslCAInfo "C:/Users/zhouh/.gitcerts/ca-bundle.crt"`（保留了全部原始 CA，只多信任这一个）
3. 重新开启 Steam++ 的 GitHub 加速后 push 成功

**如何避免**：
- 遇到"证书 issuer 不对"，先查本机代理/加速软件，**不要**用 `http.sslVerify false` 绕过——那等于对所有中间人敞开，代码可被静默替换
- 需要查 GitHub 是否可达，用 `openssl s_client` 看是"证书问题"还是"TCP 不通"，两者修法完全不同
- 本地 CA 覆盖写在 `~/.gitcerts`，不污染 Git 安装目录，重装 Git 后只需重配一行

## 2026-10-31 · strcmp 用裸 char 比较，≥0x80 字节的大小关系翻转

**现象**：
`my_strcmp` 9 条用例全过，`-Wall -Wextra` 零警告，但语义与 C 标准不一致。标准规定逐字节按 `unsigned char` 比较，实现里直接写 `a[i] > b[i]`，用的是裸 `char`。

**复现条件**：
必现，但只在字符串含 ≥0x80 的字节时暴露：
- `"\xC3\xA9"`（é）vs `"z"` → 标准返回正数（0xC3=195 > 'z'=122），该实现返回负数（`(char)0xC3` = -61 < 122）
- 纯 ASCII 输入永远不触发。所有练习题、英文标识符、数字串都在 ASCII 域内，所以测试全绿是**假象**

**定位过程**：
1. 用例全过 → 第一反应是怀疑测试漏了边界
2. 手推 `"abc" vs "abcd"`（比到 `'\0'`）、`"" vs "a"`、`"Z" vs "a"` → 都对，循环条件用 `||` 而非 `&&`，这个最容易踩的坑反而躲过去了
3. 既然边界没问题，转头查「被测值本身的类型」→ `a[i]` 是 `char`，而 C 标准对 `strcmp` 的定义是比较 `unsigned char`
4. 查 `char` 的符号性：这是**实现定义**的，x86 上的 MinGW 默认有符号，`(char)0xC3 == -61`
5. 结论：ASCII 域内两种语义完全等价，所以本地测不出来；一旦字符串来自串口原始字节（中文、0xFF 协议头）就翻转

**根因**：
C 的 `char` / `signed char` / `unsigned char` 三兄弟里，裸 `char` 的符号性由实现决定。标准库所有「按字节比较」的函数（`strcmp` / `strncmp` / `memcmp`）一律按 `unsigned char` 语义定义。直接拿 `char` 做大小比较，在字节 ≥0x80 时结果与标准相反。

**修复**：
```c
unsigned char ca = (unsigned char)a[i];
unsigned char cb = (unsigned char)b[i];
if (ca != cb) return (int)ca - (int)cb;
```

**如何避免**：
- 凡是「按字节比大小」，先转 `unsigned char` 再比。这是规则不是技巧
- 测试集必须含 ≥0x80 的字节（中文 / 0xFF），否则这类问题测不出来。纯 ASCII 全绿不代表对
- **更阴的一层**：ARM 的 AAPCS 规定裸 `char` 是**无符号**的（`arm-none-eabi-gcc` 遵守），所以这段代码在 PC 上错、烧到 STM32 上反而"对"。反过来也成立——PC 上验证过的东西，不能假设板子上行为一致。凡是依赖 `char` 符号性的代码，跨平台就是薛定谔的 bug
- 面试可这样讲：`char` 符号性是实现定义的，标准库比较函数按 `unsigned char` 定义，所以 `strcmp("é","z")` 与 `(char)` 直接比结果相反；而 ARM 与 x86 的默认符号性不同，这类 bug 只在特定平台暴露

## 2026-11-04 · 程序一条输出都没有，退出码 139

**现象**：
`p06_bug.exe` 跑完屏幕上**一个字都没有**，连 `main` 第一行的 `printf("=== p06 ...")` 都不见踪影。`echo $?` 得到 139。

**复现条件**：必现。同一份代码前一天跑骨架时是正常打印 `12 通过 8 失败`，写完四个函数体之后才变成空白。

**定位过程**：
1. 先看退出码：139 = 128 + 11 = **SIGSEGV**。桌面是 `Segmentation fault`，板子上就是 HardFault
2. 第一条 `printf` 都没出来 → 不是崩在测试中途，而是崩在**第一行输出之前**？不对，`printf` 早就执行过了 → 判定为**输出被缓冲**：stdout 接管道/文件时是块缓冲（4KB 起），进程被信号杀死时**缓冲区不会 flush**，所以已经打印的内容全部丢掉。这一条是本次排障最关键的一步，否则会误以为"连第一句都没跑到"
3. 既然崩在中途，用二分定位：把 `set_name` 的 `src == NULL` 分支临时补上 `return;` 再跑 → 输出全出来了，`19 通过 1 失败`，说明崩点就在那条 `set_name(&s, NULL)` 断言上，其余三个函数是好的
4. 回看代码：`if (src == NULL) { s->name[0] = '\0'; }` ——置完空串没有 `return`，控制流继续往下走 `src[i]`，`src` 是 NULL，`NULL[0]` 就是解引用 0 地址

**根因**：
失败分支只处理了"数据"没处理"控制流"。`src == NULL` 时把 `name` 置成了空串，但函数没有在此结束，紧接着的 `while` 条件里 `src[i]` 解引用了空指针。**`if` 块写完要明确回答"然后呢"**——是 `return`，还是刻意往下走。

**修复**：
```c
if (src == NULL)
{
    s->name[0] = '\0';
    return;              /* 少了这一行就是 139 */
}
```

**如何避免**：
- 凡是"参数非法 → 就地降级并结束"的守卫分支，写成 `return` 收尾；宁可多一行 `return`，不要让控制流靠上下文记忆往下走
- 看到"**零输出 + 139**"先想到 stdout 缓冲，不要以为程序没启动。要立刻看到崩溃前的输出，用 `stdbuf -o0 ./a.out`，或在 `main` 开头 `setvbuf(stdout, NULL, _IONBF, 0)`。**板子上串口是逐字节发的，桌面是块缓冲——同一份代码在两边看到的现象可以完全不同**
- 单元测试里所有"传 NULL 不崩"的断言，必须在**写完实现之后立刻跑一遍**，它专门抓这类漏 `return`

## 2026-11-04 · 修 bug 时把两个"长度"宏对调了

**现象**：
修完 `set_name` 的段错误后，`set_name(&s, "temp")` 断言失败：期望 `"temp"`，实际 `"tem"`。同时 `name_of(3)` 依然返回非 NULL 的垃圾指针。

**复现条件**：必现。名字超过 3 个字符就一定被截断。

**定位过程**：
1. 上一轮的问题清单是三条：`set_name` 漏 `return`、`name_of` 用错长度宏、`qsort` 的 `n` 类型
2. 改完再跑，`name_of(3)` 还是 FAIL → 说明第 2 条没动
3. 打开 `set_name` 一看，循环上界从 `NAME_LEN - 1` 变成了 `NAMES_N` → **上一轮指出该改的地方没改，指出的那个宏反而被搬到了另一个函数里**
4. 两个宏的值：`NAME_LEN = 8`（`s->name` 的字节数）、`NAMES_N = 3`（`NAMES[]` 的元素个数）。搬到 `set_name` 里等于把 8 字节缓冲区限制成 3 字节

**根因**：
两个宏名字都带"长度"，但**量的不是同一块内存**。改代码时把"要修的东西"当成了"要挪的东西"，于是修好一处、改坏一处——比原来更危险，因为原来的 bug 有明确报错，新引入的 bug 是"看起来正常但数据被截断"。

**修复**：
```c
/* name_of：量的是 NAMES[] 有几个元素 */
if (idx >= 0 && idx < NAMES_N)

/* set_name：量的是 s->name 有几个字节，且要留一位给 '\0' */
while (i < NAME_LEN - 1 && src[i] != '\0')
```

**如何避免**：
- 改之前先问一句"**这个常量描述的是哪块内存**"，把答案写在宏名旁边或注释里
- 一次只改一处、跑一次测试。三处一起改，测试变红时无法判断是哪一处引入的
- 同一作用域里出现两个名字相近、语义不同的宏（`NAME_LEN` / `NAMES_N`、`BUF_SIZE` / `BUF_N`），是真实代码库里的高频陷阱，命名时就把"字节"和"个数"区分开（如 `NAME_CAP` / `NAMES_COUNT`）

## 2026-11-05 · 空表尾插把新节点接到了自己身上（自环，死循环）

**现象**：
`test_list.exe` 打印到 `[PASS] 空表尾插后 head 不为 NULL` 之后再也不动了。不报错、不崩溃、不返回，进程一直挂着，20 秒后被 `timeout` 杀掉（退出码 124）。单独测那一个节点：`head->next == head`。

**复现条件**：必现，只在**空表上第一次尾插**时触发。先头插再尾插完全正常，所以肉眼过代码时不觉得有问题。

**定位过程**：
1. 输出停在第 144 行断言之后，下一句是第 145 行 `list_push_back(&L, 2)` → 卡在**第二次**尾插，不是第一次
2. 写最小复现：空表、只 `push_back(42)` 一次，打印 `head` 与 `head->next` 两个地址 → **完全相同**
3. 回看代码：`if (l->head == NULL) { l->head = p; }` 没有 `else`，控制流继续走到下面的尾插三行：`m = l->head`（等于 `p`）、`for (; m->next != NULL; m = m->next)` 一次都不转、`m->next = p` → `p->next = p`

**根因**：
把 `l->head = p` 当成了"空表分支的完成"，但它只是一句**赋值**，不是分支的**终点**。空表时既走了"设 head"，又走了"挂到尾巴"，而此刻唯一的节点就是 `p` 自己。失败形态是**卡死**而不是崩溃：`head->next` 非空，任何 `while (p != NULL)` 的遍历都出不来。

**修复**：
```c
p->value = v;
p->next  = NULL;                 /* 先装修完，再进门 */

if (l->head == NULL)             /* 空表：它就是唯一的节点 */
{
    l->head = p;
}
else                             /* 非空：走到尾巴挂上去 */
{
    list_node_t *m = l->head;
    while (m->next != NULL) m = m->next;
    m->next = p;
}
```

**如何避免**：
- 空表 / 非空是**互斥**的两条路，必须 `if / else`。写成"先补 head，再统一走尾插"＝让空表把两条路都走一遍
- 节点先初始化字段再挂进链表，否则 `head` 会短暂指向一个 `value`、`next` 全是垃圾的节点，中间任何一句调试 `printf` 都会踩到
- **死循环比崩溃难查**：没有退出码、没有报错、没有 core dump，只有"不动了"。链表遍历一卡住，先怀疑有没有环——数节点数到 `count` 就该停，或者用快慢指针

## 2026-11-05 · free 了一个栈上的容器指针

**现象**：
空链表上调用 `list_remove(&L, 5)`，进程直接消失。前面加 `fflush(stdout)` 的那行 `printf` 能看到，之后的输出一个字都没有，退出码非 0。

**复现条件**：必现，只在 `l->head == NULL` 这条路径上。

**定位过程**：
1. 输出断在调用点之前、退出码非 0 → 崩在函数内部，不是"返回了错误的值"
2. 看函数开头：`if (l->head == NULL) { l->count--; free(l); return 1; }` —— `l` 的类型是 `list_t *`
3. 调用处是 `list_t L;` 局部变量，`&L` 是**栈地址**。`free()` 只接受 `malloc` / `calloc` / `realloc` 返回的地址

**根因**：
把"链表容器"和"链表结点"混为一谈。该释放的是 `l->head` 串起来的那串结点，`l` 本身是调用者的容器，所有权不在这个函数手里。而且空表根本没删到东西，语义上应该返回 0，不是 1。

**修复**：
```c
if (l->head == NULL) return 0;   /* 空表没有可删的，什么都不碰 */
```

**如何避免**：
- 写 `free(x)` 前先自问：**这个地址是谁 malloc 的？** 答不出来就不能 free
- 函数只释放"自己拥有的内存"：`list_destroy` 释放结点，**不释放容器**；容器什么时候死由创建它的人决定（"谁创建谁释放"）
- 更隐蔽的情况：如果容器真是 `list_create()` 里 malloc 的，这行不会崩，而是变成 use-after-free——容器已释放，后续每个 `l->head` 都在读脏内存，程序会在几百行之外炸。**能当场崩的 bug 是好 bug**

## 2026-11-06 · if 后面少花括号，守卫拦错了句子

**现象**：
`encode_packet(&msg, buf, 16)` 正常调用，返回 7，`buf[1..6]` 全对，但 `buf[0]`（tag）永远是 `0x00`。改成 `encode_packet(NULL, buf, 16)` 想验证守卫，进程直接段错误（退出码 139）。`gcc -Wall -Wextra -Wconversion` 全程零警告。

**复现条件**：
必现。只要 `if` 体和后面第一条赋值之间没有花括号，三个条件全为假时就会跳过第一条语句。

**定位过程**：
1. 测试只红了一条（第 0 字节），其余 5 条全绿 → 说明循环体、移位、大小端都没问题，问题只在 offset 0
2. 打印 `buf[0]` 前后值 → 调用前是 0，调用后还是 0，那段赋值压根没执行
3. 回看函数头：`if (in == NULL || buf == NULL || cap < 7)` 后面直接跟 `buf[0] = in->tag;` 而**没有 `return 0;`** → `if` 的体就是那条赋值本身
4. 于是语义完全反了：条件为假（正常调用）时跳过 `buf[0]`；条件为真（出错）时才执行它，然后继续往下写 `buf[1]`，NULL 输入就解引用崩

**根因**：
`if` 不带花括号时，它的体永远只有紧跟着的**一条语句**。想表达的「出错就撤」没写出来，`return 0` 缺失，使守卫变成了「出错时才写第一字节」。

**修复**：
```c
if (in == NULL || buf == NULL || cap < 7)
{
    return 0;
}
```

**如何避免**：
- `if` 一律带花括号（MISRA C Rule 15.6 强制这条），收益不是好看，是**以后往守卫里加语句时不会重新踩**——加第二句时，被保护的仍然只有第一句，而且编译器和测试都不会告诉你
- 断言要覆盖「第 0 字节」这种**第一个被写的位置**，只测中间字节测不出漏写
- 失败路径要测**不改缓冲区**：预填 `0xAA`，调用失败后检查一个字节都没动。这一条能同时抓越界写和漏写

## 2026-11-06 · 31/33 全绿，函数在另一条路径上是未定义行为

**现象**：
`is_aligned(ptr, 4)` 三条断言全过，编译有一条 `warning: control reaches end of non-void function [-Wreturn-type]`。同一份源码，`-O0` 编出来未对齐地址返回 **1**（错），`-O2` 编出来返回 **0**（对）。

**复现条件**：
必现，只在「指针未对齐」这条路径上。原测试三条用例分别走了「已对齐」「NULL」「align == 0」，**没有一条走未对齐路径**。

**定位过程**：
1. 只看测试：全绿，没有线索
2. 看编译输出：`-Wreturn-type` → 函数可能执行到末尾
3. 读代码：`if (对齐) return 1;` 之后就没有语句了，`return 0` 缺失
4. 补两条断言（`s1 + 1` 未对齐、`s1 + 2` 按 2 对齐），失败的正是未对齐那条
5. 用 `-O0` / `-O2` 各编一次对比 → 同一份源码两个返回值，确认是 UB 不是逻辑错

**根因**：
有返回值的函数执行到末尾属于未定义行为，返回值由编译器决定。`-O0` 保留了 `eax` 里的残留值（恰好是 1），`-O2` 直接按「这条路径不可达」优化，返回 0。**这不是「恰好对了」，是运气。**

**修复**：
```c
return ((uintptr_t)p % align) == 0;   /* 比较表达式本身就产出 0/1 */
```

**如何避免**：
- 编译出现 `-Wreturn-type` 一律当编译失败处理，加 `-Werror` 最省心
- 写断言时列出**所有分支**：`NULL` / 非法参数 / 条件成立 / 条件不成立。三条全绿不代表第四条也对
- 这类 bug 在板子上往往等换优化等级（`-O2` 上板）或换编译器版本才发作，是「本地好好的、上板就死」的典型来源

## 2026-11-06 · 循环里的 >> 32：x86 给一个值，ARM 给另一个

**现象**：
`bug3_fixed` 里 `for (int i = 1; i < 5; i++) buf[i] = (m->value >> (i * 8)) & 0xFF;`，`i = 4` 时移位量是 32。x86 上 `buf[4]` 得到 `0x44`（看着像低字节，其实错了），编译零警告。

**复现条件**：
必现。移位量等于或大于类型位宽就是 UB，而移位量是循环变量时编译器不做值域推断，一句警告都没有。

**定位过程**：
1. 测试报 `第 4 字节 value 高字节 期望 17，实际 68` → 68 是 `0x44`，正好是 value 的最低位字节
2. 手算：`0x11223344 >> 32`。C 标准要求移位量 `< 32`，这条越界
3. 实测 `v >> 32`（变量）与 `v >> 0` 结果完全相同 → x86 的移位指令只取移位量低 5 位，`32 & 31 = 0`
4. 换成常量 `v >> 32` 再编译 → 立刻报 `-Wshift-count-overflow`。差异只在「移位量是不是编译期常量」

**根因**：
右移位数 ≥ 类型位宽是未定义行为。x86 硬件把移位量按 31 取模，ARM 的 `LSR` 在移位量 ≥ 32 时直接给 0 —— 同一份源码两个平台两个答案。

**修复**：
```c
for (int i = 0; i < 4; i++)
{
    buf[1 + i] = (uint8_t)((m->value >> (i * 8)) & 0xFFu);
}
```
把「数组下标从 1 起」和「移位量从 0 起」解耦：下标基准单独加在 `buf[1 + i]` 上，移位量老老实实 0..24。

**如何避免**：
- 循环里出现 `x >> (i * 8)` 这类模式，先算一遍 `i` 的最大值，确认 `< sizeof(x) * 8`
- 定长序列化别手写循环，封装成 `write_u32_le(p, v)` 一处实现，调用点多的地方就少犯一次差一错误
- 把常量换成变量是警告消失的重灾区：凡是「`i` 参与移位 / 数组下标 / 掩码宽度」的表达式，编译器基本帮不上忙

## 2026-11-07 · 循环右移 8 次当成了位反转（函数恒等于输入）

**现象**：
`reverse_bits8(0x96)` 期望 `0x69`，实际返回 `0x96`；`0x01` 返回 `0x01`、`0x80` 返回 `0x80`。三条断言全红，且实际值**全部等于输入本身**。而 `0x00`、`0xFF` 和「反两次回到原值」那条自检全绿，编译零警告。

**复现条件**：
必现。函数做的是 8 次「循环右移 1 位」，转满一圈回到原点。

**定位过程**：
1. 三条失败的实际值是 150 / 1 / 128，正好是 `0x96` / `0x01` / `0x80` → 不是「算错一位」，是「根本没变」
2. 读循环体：`b = (b >> 1) | ((b & 1) << 7)` —— 这是标准的 8 位环形右移，bit0 出队、从 bit7 进来
3. 手推 `0x96` 走两步：`0x96 → 0x4B → 0xA5 …`，环移是**旋转**，8 次必然回到起点
4. 反过来看为什么只红 3 条：`0x00` 和 `0xFF` 是自反值（反转后等于自己），「反两次回原值」对恒等函数更是必然成立

**根因**：
把「反转」理解成了「旋转」。反转是镜像（bit0 ↔ bit7、bit1 ↔ bit6），每一位往**相反方向**走；旋转是平移，所有位朝**同一方向**挪，只有出界的那一位绕回来。单个变量原地操作只能做平移，做不出镜像。

**修复**：
```c
uint8_t reverse_bits8(uint8_t b)
{
    uint8_t r = 0;
    for (int i = 0; i < 8; i++) {
        r = (uint8_t)((r << 1) | (b & 1u));   /* r 往高位长 */
        b >>= 1;                              /* b 往低位缩 */
    }
    return r;
}
```
分治版（无循环，3 步走完，与数据无关）：
```c
b = (uint8_t)(((b & 0xF0u) >> 4) | ((b & 0x0Fu) << 4));   /* 高低半字节互换 */
b = (uint8_t)(((b & 0xCCu) >> 2) | ((b & 0x33u) << 2));   /* 每 2 位一组互换 */
b = (uint8_t)(((b & 0xAAu) >> 1) | ((b & 0x55u) << 1));   /* 每 1 位一组互换 */
```

**如何避免**：
- 镜像类操作必须有两个变量朝相反方向走。只有一个变量时，先问一句「我要的是平移还是镜像」
- 测试集必须含**不自反**的值（`0x96` / `0x01` / `0x80`）。`0x00` / `0xFF` 这类值对镜像操作没有任何分辨力，写错也过
- 「f(f(x)) == x」是必要不充分条件，恒等函数也满足。想验证反转，必须验证单向结果

## 2026-11-07 · 一句 `v >> 1;` 什么都没做，测试却全绿

**现象**：
`count_ones` 循环体里写了三句：`v &= (v - 1);`、`v >> 1;`、`n++;`。编译报 `warning: statement with no effect [-Wunused-value]`，但 6 条断言全过（0 / 1 / `0x80000000` / `0xA5` / `0xFFFFFFFF` / 32 个单 bit 值）。

**复现条件**：
必现。`v >> 1;` 少了赋值号，是个纯表达式语句，算完把结果丢掉。

**定位过程**：
1. 警告直接指向 `v>>1;` → 一眼看出缺 `=`
2. 先确认「补上 `=` 会不会也过」：写了个对照程序，遍历 0..99999 比较「纯 Kernighan」和「Kernighan + 右移一位」两版 → **不一致个数 0**
3. 推原因：`v &= (v - 1)` 清掉的是最低的那个 1，它右边原本全是 0，所以清零后最低位必然是 0。再 `>>= 1` 移出去的永远是 0，一个 1 都没丢
4. 结论：写错（空语句）和写对（多余移位）**都能通过测试**，这个 bug 只有编译器警告和读代码能抓到

**根因**：
`v >> 1` 是表达式，不是语句的效果来源。C 里「算一个值然后丢掉」的语句没有任何副作用，编译器只会报 `-Wunused-value`。而这题的算法本身对「多做一次无操作」免疫，所以测试永远抓不到。

**修复**：
```c
int count_ones(uint32_t v)
{
    int n = 0;
    while (v) {
        v &= (v - 1);
        n++;
    }
    return n;
}
```

**如何避免**：
- `-Wunused-value` 别关，编译有警告一律当失败处理（11-06 立过这条规矩，这是第三次撞上）
- 写完一个循环体，逐句问「这一句改变了什么状态」；答不出来就删掉
- 测试全绿只证明「结果对」，证明不了「每一行都有用」。冗余语句要单独看

## 2026-11-07 · 代码对了，注释把方向标反了

**现象**：
`swap_u32` 四条断言全过，但第一行 `uint32_t a = v >> 24;` 后面挂着注释 `// 低8位`。

**复现条件**：必然发生，注释错误不影响运行，所以测试全绿也不会提示。

**定位过程**：
1. 测试全绿，转去逐行读注释
2. `v >> 24` 把 bit31..24 搬到 bit7..0，那是**最高**字节（byte3），不是低 8 位
3. 真正的低 8 位是第四行 `(v & 0xff) << 24` 里的那个 `v & 0xff`

**根因**：
写的时候脑子里想的是「这一项的结果落在最低的 8 位」，注释记的是**结果的去处**，而代码本身表达的是**数据的来源**。两个视角拧在一句话里，就写反了。

**修复**：
按「来源 → 去处」标，方向明确到不用推：
```c
uint32_t a = v >> 24;            /* byte3 → byte0：最高 8 位搬到最低位 */
a = a | ((v >> 8) & 0xff00);     /* byte2 → byte1 */
a = a | ((v << 8) & 0xff0000);   /* byte1 → byte2 */
a = a | ((v & 0xff) << 24);      /* byte0 → byte3 */
```

**如何避免**：
- 位操作的注释一律写「从哪一位 → 到哪一位」，不要写「低 8 位」「高字节」这种**不带方向的名词**，读者无法判断你说的是来源还是结果
- review 时注释和代码分开读：先看注释判断意图，再看代码验证行为，两边不一致就是 bug（这次就是不一致）
- 测试证明不了注释。凡是「代码能跑」就跳过注释检查，错误就会一直在仓库里躺着
